# Append-only comments and separate audit trail

Each record has a concrete typed context. Threads carry visibility (participants or authorized staff scope) and immutable original author. A comment version records UUID, thread ID, sequential version, predecessor ID, author user ID, acting-role snapshot, DB timestamp and bounded plain text. First version has no predecessor. Corrections append by original author with predecessor pointing to latest version in same thread. Other participants add a new thread/reply, not impersonated corrections. Latest version is a projection; complete version chain is visible to authorized participants.

Transaction locks thread, checks record authorization and visibility, enforces predecessor/current head and appends. Unique predecessor and thread+version prevent concurrent branching; one correction succeeds, the other receives conflict and can rebase. Cross-thread predecessor rejected by composite FK/validated constraint. No UPDATE/DELETE endpoint. Runtime database role has no update/delete/truncate on comment versions; insert via narrow append function only. Immutable triggers reject changes even if application code accidentally attempts them. FK cascades cannot delete comments. DB schema owner is separate and absent from app credentials.

Identity/role/timestamp derived by server/DB; client cannot spoof them. Role snapshot does not confer future access. Viewing old versions rechecks current context authorization. Plain text escaped at rendering, no raw HTML; bounded length and rate limits; comment previews never leak into unauthorized lists. Full student identities appear only to authorized scopes.

Audit records are separate, append-only, structured security/operations events: authentication outcomes (safe identifiers), user/role/assignment/policy changes, approval/reassignment, reservation/expiry, issue/return/inspection, identity correction, movement/adjustment, import/export and denied sensitive actions. Include actor, acting role, target, correlation, DB timestamp, reason and minimized safe before/after fields. Never log passwords, session/SSO tokens, complete exports or unnecessary comment contents. Business-success audit commits with operation; rejected attempts use independently durable security logging without falsely recording success.

Runtime can append audit only through controlled pathway; no mutation. Log reads/exports are scoped and audited. Authorized operators may later ship signed/hash-anchored batches to separately administered immutable storage, only after integration approval. A hash chain inside the same writable database does not defeat a malicious superuser. Database administrators/backups remain a residual threat; separation of duties and recovery/reconciliation are required.

Append-only conflicts with potential lawful erasure/redaction obligations. No ordinary deletion; a separately authorized privacy process may restrict visibility or anonymize identifying fields under approved retention rules while preserving permitted evidence. Do not invent a retention period or promise that immutable content can never be removed by privileged infrastructure owners. Resolve P14 before production.
